## Context and Motivation

Vetify is currently React (Vite) + Express + Daml/Canton ledger + PQS (see main `CLAUDE.md`). The case for moving off Canton/Daml entirely:

- **No actual need for blockchain guarantees.** The product's core value (Murabahah financing workflow, multi-party approvals, audit trail) doesn't depend on Canton's specific properties — a well-designed relational schema with row-level security and an append-only audit table can deliver the same practical guarantees the application actually relies on today.
- **Cost/ops complexity.** The current stack requires `dpm sandbox`, a PQS/Scribe sidecar version-locked to the SDK, Docker's `network_mode: host` workaround, and re-allocating 9 parties + hand-registering governance contracts after every restart (per `docs/local-dev-startup.md`) because the Canton sandbox has **no persistent storage**. A traditional Postgres database has none of this operational overhead.

This would be a **big-bang rewrite**: build the new stack completely, verify it, then cut over — not an incremental migration run alongside the old one.

Two requirements constrain every design decision below:
1. **Per-party data isolation must remain a real architectural guarantee** — the equivalent of Canton's signatory/observer sub-transaction privacy — enforced at a layer no buggy route handler can bypass, not just "the app remembers to filter."
2. **Full data-model fidelity.** All ~95 Daml templates/records get a Postgres equivalent, including the 54 of 64 `Murabahah.daml` templates that have no current backend route (disputes, collections/direct-debit, covenants, regulatory/SAR reporting, collateral valuation, force majeure, etc.) — so those features can be wired up later without another schema migration.

The new backend would consolidate into a **single Next.js app** (API routes / route handlers absorbing the current Express server) rather than keeping today's two-service split.

## Current-State Research Findings

These facts, gathered from the live codebase, underpin the design:

- **Scope**: ~95 templates/records across `daml/Vetify/{Types,Onboarding,Compliance,Financing,Murabahah,Reporting,Governance,FinancingProvider}.daml` (8,110 lines total). `Murabahah.daml` alone defines 64 templates; only **10 of those 64 (16%) are reachable from any backend route today** (`backend/src/routes/{contracts,financing}.ts`). The other 54 — grouped roughly into Ibra'/charity (8), collateral/Rahn (5), collections/direct-debit (4), default/recovery/dispute (10), covenants/monitoring (5), regulatory/SAR (7), force majeure/misc (5), asset-acquisition support (6), Wad/Wakala terminal states (4) — are either created as dead side-effects of a wired choice or entirely unreferenced from the API layer.
- **Backend chokepoint**: `backend/src/repository.ts` (432 lines) is the only file that imports `canton.ts` (447 lines, ledger client) and `pqs.ts` (281 lines, PQS read-side); all 5 route files (`onboarding.ts`, `financing.ts`, `contracts.ts`, `policy.ts`, `providers.ts`) go through it exclusively. This means route *signatures* can survive a rewrite even though `repository.ts`'s internals are fully replaced.
- **`agents/src/scoring/*` is already Canton-agnostic** — pure TypeScript functions over evidence JSON (`scoreVerification`, `scoreCompliance`, the 5-engine `scoreUnderwriting`, `scoreDelinquency`, `aggregatePortfolio`, `classifyShariahCompliance`). These need zero changes in a migration.
- **Auth/party model today**: many human logins share one Canton party per role — `users.party_role` selects which shared, backend-held JWT to act as; it is **not** 1 user : 1 ledger identity. The one exception is self-serve FI signups, which get a dynamically allocated per-tenant Canton party (`fi:<userId>`), stored on that user's row. `audit_log` (`id, user_id, username, display_name, party_role, action, contract_id, details jsonb, occurred_at`) is already plain Postgres and is the *real* individual-attribution record today — the ledger itself only ever sees the shared party name.
- **Dual-controller choices today** (e.g. `Approve` = `controller verifier, vetify`) are exercised as one ledger transaction with both party JWTs supplied by the same backend process — not genuine separation of authority, since one Express process holds every party's JWT simultaneously. The one place that *does* split authority into two real transactions/sessions is `policy.ts`'s maker-checker flow (`propose` as `vetify` → `EndorseByRiskCommittee` as `riskCommittee` → `ApprovePolicyChange` as `vetify`, with `approvedBy != proposedBy` and an approver-registry check) — its own code comment explains this split was deliberate specifically so a single combined call can't fake dual authorization.
- **Greenfield confirmed**: `CLAUDE.md` states the Canton sandbox is in-memory-only — "every party ID and every ledger contract is gone after any Docker/sandbox restart." There is no durable production ledger data anywhere to migrate. Only `users`, `audit_log`, `notifications`, and `creditworthiness_webhooks` (already plain Postgres tables in `infra/postgres/init.sql`, unrelated to the ledger) would carry forward as-is.
- **Frontend**: `react-router-dom` v6 + `@tanstack/react-query`, 27 page components across 5 portals (business: 5, FI: 6, vetify/platform-ops: 10, compliance: 2, risk-committee: 1, plus 3 top-level). `frontend/src/api/client.ts` (~3,600 lines) is largely `Raw*`/`adapt*` boilerplate working around the Daml v2 JSON Ledger API's quirk of encoding `Int`/`Decimal` as JSON strings on both read and write.
- **Agents' Canton-coupled files**: `agents/src/mcp/canton-client.ts` (v2 ledger client, shared by MCP tools and the Supervisor), `canton-server.ts` (exposes `get_active_contracts`/`exercise_choice`/`create_contract` as MCP tools), `agents/supervisor.ts` (polls the ledger directly every 10s, not just via MCP), `backend/src/canton-oidc.ts` (participant OIDC token acquisition).

## Proposed Architecture

```
Next.js app (single deployable)
├── app/{business,fi,vetify,risk-committee}/**/page.tsx   ← 27 pages, file-routed by portal
├── app/api/**/route.ts                                    ← replaces Express routes/*.ts
├── lib/domain/*.ts                                         ← one function per former Daml choice
├── lib/scoring/*.ts                                        ← agents/src/scoring/*, moved verbatim
├── lib/auth/*.ts                                           ← session/TOTP, ported from backend/src/auth.ts
└── lib/db.ts                                                ← pg Pool + withTransaction() (sets RLS GUCs)
        │
        ▼
Postgres (RLS-enforced)  ←── supervisor.ts / agents (in-process, calling lib/domain directly)
```

Net effect: one database, one deployable web app, one background worker process (the Supervisor) — replacing today's ledger + PQS sidecar + Express + Vite + agents-as-separate-MCP-client arrangement.

### 1. Postgres Schema Design

**Derivation rule**, applied to all ~95 templates/records:
1. Every Daml `template` → one Postgres table (snake_case name).
2. Value-type `data` records referenced only from one parent template's fields (`BusinessProfile`, `ComplianceCheck`, `MurabahahTerms`, `RiskAssessment`, `*ScoringWeights`, etc.) → a `jsonb` column on that table, not a normalized table. These are never queried cross-template today, and `repository.ts`'s existing JSON-path predicates (`payload->>'status'`) translate directly to SQL.
3. `Optional (ContractId T)` arguments that exist only because Daml 3.4.11/LF 2.2 has no contract keys (`policyCid`, `advisorCid`, `eddCaseCid`, etc.) → collapse to plain foreign keys, resolved server-side by the transaction function via `SELECT`. This removes an entire class of caller-side ContractId lookup/passing that exists purely as a Daml-limitation workaround — a genuine simplification, not just a translation.
4. Daml enums (`ReviewStatus`, `MurabahahStatus`, `FinancingStatus`, …) → native Postgres `ENUM` types, using the **same constructor names**, so `frontend/src/api/client.ts`'s hand-written status union types would need zero changes.
5. Optional/dual-signatory party fields → nullable/plain `text` columns referencing a `party_roles` table (see RLS section below), not junction tables.

**Archived-contract-implies-terminal-state semantics** (replacing Daml's immutable-contract model):
- No physical deletes, ever. Every table gets `archived_at timestamptz` (null = live) plus `superseded_by_id`/`superseded_by_kind` where a choice produces a different successor template.
- Partial unique indexes replace lost contract-key uniqueness, e.g.:
  ```sql
  CREATE UNIQUE INDEX one_active_onboarding_per_cac
    ON business_onboarding ((kyc->>'cacRegNumber')) WHERE archived_at IS NULL;
  ```
  This is actually **stronger** than the status quo — `daml/Vetify/Onboarding.daml`'s own comment documents that `(business, kyc.cacRegNumber)` uniqueness is currently an unenforced, caller-side-only convention on SDK 3.4.11/LF 2.2 (no contract keys).
- Choices that did `create this with field = X` (archive-and-recreate under the same logical identity) collapse to a plain `UPDATE` — the single biggest structural simplification available, since that pattern only ever existed because Daml contracts are immutable.
- Choices that create a genuinely new successor contract become one Postgres transaction that `UPDATE`s the source row's `archived_at`/`superseded_by_id` and `INSERT`s the successor row — preserving the same atomicity a single Canton transaction gave.

**Representative vertical slice** (Stage 1–4: Onboarding → Verification → Compliance → ApprovedBusiness) as the schema convention-setter:
- `party_roles(id, role_kind, owning_user_id)` — backs RLS; every other table FKs into it instead of storing raw party strings.
- `business_onboarding` — `profile jsonb`, `kyc jsonb`, `status review_status`, `documents jsonb`, `document_history jsonb`, `archived_at`, `superseded_by_id`; partial unique index on `kyc->>'cacRegNumber'` where live.
- `verification_result`, `compliance_review`, `edd_case` (the G14 EDD checklist), `compliance_result`, `approved_business` — same shape pattern, each carrying its module's `data` records as JSONB columns.

**Pattern for the remaining ~90 templates**: the same 5-step derivation applies mechanically to every other module. `Murabahah.daml`'s 64 templates — including all 54 currently-unwired ones — would all get full tables even without a route yet, since that's schema-only work and is exactly what full data-model fidelity requires. `Governance.daml`'s registries (`AuthorizedOfficer`, `PolicyApprover`, `AuthorizedAssessor`, `AuthorizedSentinel`, `AuthorizedAdvisor`, plus `Compliance.daml`'s `AuthorizedReviewer`) become small `active boolean` lookup tables mirroring their existing register/deactivate/reactivate lifecycle. Given the volume (~95 largely mechanical `CREATE TABLE`s), a small codegen pass over the Daml source's `template`/`with`/`signatory`/`observer` blocks would be worth building rather than hand-authoring all of them — the source is consistent enough for this to be reliable.

### 2. Row-Level Security Design

Maps the 9 Canton parties (`business`, `vetify`, `financialInstitution`, `verifier`, `assessor`, `sentinel`, `regulator`, `riskCommittee`, `advisor`) onto **Postgres session variables**, not separate DB roles/logins — one application DB role (`vetify_app`) owns all tables, mirroring today's "single process holds every party's JWT" trust boundary exactly. Session variables (`SET LOCAL`, not `SET ROLE`) are chosen because they're pool-safe — `SET LOCAL` inside a per-request transaction works cleanly with pgbouncer transaction-mode pooling, whereas `SET ROLE` doesn't survive the pool boundary reliably.

**Per-request wiring** (a Next.js middleware would set these from the session JWT — a direct translation of today's `SessionPayload`, which already carries `partyRole`/`cacRegNumber`/`financialInstitutionPartyId`):
```sql
BEGIN;
SET LOCAL app.current_party_role = 'business';        -- from session.partyRole
SET LOCAL app.current_party_id = 'fi:42';              -- static role name, or fi:<userId> for a dynamic FI tenant
SET LOCAL app.current_cac_reg_number = '...';           -- business tenant scope
-- queries --
COMMIT;
```

**Policy pattern** (generalizes across all ~95 tables from each template's signatory/observer clause):
```sql
ALTER TABLE business_onboarding ENABLE ROW LEVEL SECURITY;

CREATE POLICY visible_to_signatory_and_observers ON business_onboarding
  FOR SELECT
  USING (
    current_setting('app.current_party_role', true) IN ('vetify', 'verifier')
    OR (
      current_setting('app.current_party_role', true) = 'business'
      AND kyc->>'cacRegNumber' = current_setting('app.current_cac_reg_number', true)
    )
  );
```
Dual-signatory tables (`MurabahahContract`, `RepaymentRecord`, `RahnAgreement`) OR both signatory-column checks. Dynamic FI tenants scope by `financial_institution_party = current_setting('app.current_party_id', true)`, mirroring `canton.ts`'s existing `resolveFinancerParty()` fallback logic exactly.

**What RLS does and doesn't cover**: RLS enforces *visibility* — no route handler can leak a row by forgetting a `WHERE` clause — the direct analogue of Canton's privacy model. It does **not** enforce business-rule asserts (`ensure`/`assertMsg` guards); those stay in transaction functions and CHECK constraints (see below). Both layers would be required together.

**Individual attribution** (many-users-share-one-role) continues exactly as it does today via `audit_log` — RLS stays party-scoped, not user-scoped, which matches Canton's actual privacy model (also never per-human).

### 3. State-Machine / Choice Replacement Pattern

- **Structural invariants** (Daml `ensure` clauses) → Postgres `CHECK` constraints where SQL-expressible; a `BEFORE INSERT/UPDATE` trigger for cross-field logic (e.g. the CAC-prefix-by-businessType rule).
- **Choice preconditions** (`assertMsg` bodies) → one TypeScript transaction function per former choice, in `lib/domain/{onboarding,compliance,financing,murabahah,governance,policy}.ts`, each wrapped in a single `BEGIN`/`COMMIT` with `SELECT ... FOR UPDATE` on every row it reads-then-writes (replacing Daml's automatic optimistic concurrency via contract consumption with explicit pessimistic locking, since Postgres rows are mutable). This would be a **direct line-by-line port**: every `assertMsg` → `if (!cond) throw DomainError(sameMessage)` (preserving today's error text so `canton.ts`'s existing `toLedgerError()`→422 mapping and the frontend's error handling keep working unmodified), every `fetch cid` → `SELECT ... FOR UPDATE`, every `create X with ...` → `tx.insert(...)`, every implicit archive → an explicit `UPDATE ... SET archived_at = now()`.
- **`requireActive*` registry gates** (`requireActiveAdvisor`/`Assessor`/`Sentinel`/`PolicyApprover`/`Officer` in `Governance.daml`) → one shared helper each in `lib/domain/governance.ts`, called at the top of the relevant transaction functions — this collapses the caller-side-ContractId-resolution indirection entirely.

**Dual-controller / maker-checker mapping** — two distinct existing patterns, preserved as two distinct target patterns:
1. **Choices exercised as one transaction with both parties' authority already effectively co-held** (`Approve`/`Reject`, `BeginUnderwriting`/`RejectUnderwriting`, `FlagDelinquent`/`ResumeActive`, `RecordShariahPreCheck`, `CertifyShariahTerms`) → one transaction function, callable by a session whose role is either of the pair, recording both role names in `audit_log.details.actingRoles`. This is an honest same-shape port — no weaker or stronger a guarantee than exists today.
2. **Genuine two-transaction maker-checker** (`policy.ts`'s propose→endorse→approve precedent) — a candidate to generalize to other consequential transitions (`ApproveCompliance`, `ApproveFunding`, etc.) as a **later hardening pass**, not required for functional parity: split into a `propose` step (single role, leaves a `co_signed_by_vetify_at` column null) and a separate `cosign` step (different role, different request/session) that only then fires the terminal transition. This would be a genuine strengthening over today's actual guarantee — worth calling out as an opportunity the migration creates, not something needed just to match current behavior.

### 4. Next.js Consolidated App Architecture

```
apps/web/
  app/
    (public)/{page.tsx, login/page.tsx, signup/page.tsx}
    business/layout.tsx + {dashboard,onboarding,financing,acquisition,contracts/[id]}/page.tsx
    fi/layout.tsx + {dashboard,contracts,contracts/[id],acquisition,underwriting,provider-settings}/page.tsx
    vetify/layout.tsx + {dashboard,onboarding,compliance,compliance/[id],monitoring,registries,underwriting,agents,reports,providers,policy,dev-tools}/page.tsx
    risk-committee/layout.tsx + dashboard/page.tsx
    api/{auth,onboarding,financing,contracts,policy,providers,documents,notifications,webhooks,dev}/**/route.ts
  lib/
    db.ts                    ← pg Pool + withTransaction() setting RLS GUCs from session
    domain/*.ts               ← one file per Daml module, one function per choice
    auth/{session,middleware}.ts
    scoring/*.ts               ← moved verbatim from agents/src/scoring/
  middleware.ts               ← root auth gate (replaces app.ts's blanket requireAuth() mount)
```

**Routing**: a direct 1:1 mapping from `frontend/src/App.tsx`'s current 27 `<Route>` entries onto folder paths — same URLs preserved. `ProtectedRoute role="..."` would become a route-group `layout.tsx` per portal doing a server-side `redirect()` from a server-read session cookie — stronger than today's client-side-only guard, since it runs before any page code executes.

**Auth/session/TOTP**: `backend/src/auth.ts`'s session/TOTP functions (JWT issuance, `otplib`-based TOTP) are pure and framework-agnostic — they'd port unchanged into `lib/auth/session.ts`. Recommend switching token storage from `localStorage` to an httpOnly cookie at the same time (closes an XSS surface the current `client.ts` pattern has, and lets Server Components read sessions without a manual header). Rate limiting on login/MFA-verify would need an explicit replacement (a small Postgres-backed sliding-window counter — no Express middleware chain to lean on in Next's model).

**React Query**: `frontend/src/api/client.ts`'s ~40 hooks would port essentially unchanged — React Query works identically inside Next.js Client Components. A real simplification becomes available: Postgres returns real JSON numbers, so the `Raw*`/`adapt*` Int64/Decimal-as-string adapter layer (a large fraction of `client.ts`'s ~3,600 lines) could be deleted outright, since that layer exists solely to work around the Daml v2 JSON Ledger API's string-encoding quirk. Keeping enum wire values identical (Postgres native `ENUM`s serialize the same way Daml's did) means status-field types would need zero frontend changes.

WHERE status = 'X' AND archived_at IS NULL` calls against `lib/domain`. ## Addendum: Money Representation, Audit History, and Effort Sizing

*(Added after a design review; closes the three gaps judged serious enough to block starting Phase 0 as originally written.)*

### A. Money representation

The original §1 rule ("value-type record → `jsonb` column") would put `MurabahahTerms.assetCost/profitAmount/salePrice/installmentAmount`, `FinancingTerms.amount`, `PaymentScheduleEntry.dueAmount`, `RepaymentRecord` amounts, `LatePaymentCharity.amount`, `IbraRequest.rebateAmount`, and `RiskAssessment.recommendedLimit` inside JSON blobs, which round-trip through JS as IEEE-754 doubles — the same class of bug `CLAUDE.md` documents fighting hard to fix (`numifyWeights`). Corrected rule:

- **Every field typed `Decimal` in `daml/Vetify/Types.daml` gets its own `NUMERIC` column**, never a jsonb-buried number. `Int`-typed fields can stay as native Postgres `INTEGER`/`BIGINT` (bounded, no precision loss) and may still live in jsonb if they're part of a value record.
- `node-postgres` already returns `NUMERIC` as a JS **string** by default (`pg`'s driver-level behavior, not a config choice) — this is a feature here, not a gap. Domain logic (`lib/domain/*.ts`) must do all monetary arithmetic through a decimal library (`decimal.js` or `big.js`), never native `+`/`*` on parsed floats.
- Correction to §4's claim: the `Raw*`/`adapt*` layer in `frontend/src/api/client.ts` does **not** fully disappear. It shrinks — the Int-as-string workaround goes away since native `INTEGER`/`BIGINT` serialize as real JSON numbers — but the Decimal-as-string handling stays, because it's now correct-by-construction rather than a workaround for the Daml v2 API's encoding quirk. This is a smaller change than originally described, not the "large fraction... deleted outright" framing in §4.
- Action item for Phase 0: enumerate every `Decimal` field in `Types.daml` explicitly before generating the schema, so the codegen pass (§1) emits `NUMERIC` columns for exactly those fields and nothing else.

### B. General audit-history mechanism

§3's "archive-and-recreate collapses to a plain `UPDATE`" is the single biggest simplification the design offers — but it silently drops the field-level history that `CLAUDE.md` names as one of Canton's two core guarantees ("immutable audit trails"), and the doc only builds a replacement for one table (`business_onboarding.document_history`). Generalized fix:

- A single shared `entity_history` table (`table_name, row_id, before jsonb, after jsonb, changed_at, changed_role, action`), populated by an `AFTER UPDATE` trigger on every table using `row_to_json(OLD)`/`row_to_json(NEW)`. No per-table hand-authoring — generate the trigger from the same Daml-source codegen pass already proposed for table generation (§1's closing paragraph), so all ~95 tables get one automatically.
- This is deliberately separate from the existing `audit_log` table (action/user-level, already in `infra/postgres/init.sql`) — `entity_history` is row-state-level and exists to answer "what did this row look like before," which today only exists implicitly via Canton's contract immutability.
- Regulatory/Shariah evidentiary weight is a business question this design doesn't resolve, not just a technical one: the `advisor` (SSB) certification chain and the `regulator` observer role exist because Canton gives a tamper-evident record for a CBN NIFI-regulated product. A lightweight mitigation worth scoping (not full blockchain-equivalence) is periodically anchoring a hash (e.g. nightly Merkle root over `entity_history` + `audit_log`) to an external write-once store, so retroactive tampering is at least detectable. **This needs sign-off from the Shariah advisory board and whoever owns CBN regulatory relationship, not just an engineering decision** — flag it as an open question before committing to the migration, not an implementation detail to resolve mid-build.

### D. What Daml enforces that TypeScript won't

§3's choice→function mapping reads as a mechanical translation, but it quietly retires three guarantees Daml provides *by construction* and asks hand-written TypeScript to recreate them *by convention* instead. Each needs an explicit mitigation, not just awareness:

1. **Authorization is no longer compile-checked.** A Daml `controller X` clause makes it a compile error to exercise a choice without `X`'s signature. A `lib/domain/*.ts` function has no such backstop — a missing role check is a silent authorization bypass discovered at runtime (or in review), not build time. Across ~95 ported functions, this is the single largest new attack surface the migration introduces.
   - **Mitigation**: a shared `withAuthorization(allowedRoles, fn)` wrapper (in `lib/domain/auth-guard.ts`) that every domain function must be defined through — never call the underlying logic directly. Pair with a lint rule (an ESLint custom rule or a simple grep-based CI check) that fails the build if any exported function in `lib/domain/**` isn't wrapped by `withAuthorization`. This converts "remember to check the role" from a per-function discipline back into a structural guarantee the same way Daml's compiler did — enforced once, not re-derived 95 times.

2. **No formal atomicity model.** Daml transactions are all-or-nothing by construction; the Postgres equivalent is atomic only if every function correctly wraps its reads/writes in one `BEGIN`/`COMMIT`, with consistent lock ordering across tables (see the concurrency gap already flagged above).
   - **Mitigation**: domain functions never call `pool.query()` directly — only through a `withTransaction(fn)` helper that owns `BEGIN`/`COMMIT`/rollback-on-throw and sets the RLS session GUCs in the same block. Combined with the CI check in (1), this means every domain function is structurally required to go through both the authorization wrapper and the transaction wrapper, closing off the "forgot to wrap it" failure mode at the point of definition rather than relying on code review to catch it.

3. **SCU (Smart Contract Upgrade) safety net disappears.** `dpm build`/`dpm upgrade-check` genuinely rejects an incompatible Daml template change (e.g. a removed field) at build time (`CLAUDE.md`'s SCU lineage section). Postgres migrations have no automatic equivalent — a breaking schema change (dropped/renarrowed column) ships unless a human catches it in review.
   - **Mitigation**: a CI step running the migration runner against a snapshot of the previous schema plus a compatibility linter (e.g. `migra`/`sqlcheck`-style diffing, or a hand-rolled check for `DROP COLUMN`/`ALTER COLUMN TYPE` on any table with existing rows) that fails the build the same way `dpm upgrade-check` does today — not full parity with Daml's guarantee, but a comparable tripwire rather than nothing.

**Net framing for the doc**: this migration trades a domain-specific language with built-in signatory/atomicity/upgrade-safety guarantees for general-purpose TypeScript that must recreate those guarantees through structural wrappers and CI tripwires, not through the platform itself. That's a defensible trade given the ops-cost motivation — but it should be named explicitly as a risk with its own mitigations (as above), not left implicit in "here's how choices map to functions."

### Three real bugs found during verification (not hypothetical — each reproduced live, then fixed)

Going in, the design's addendum (section on RLS fail-open risk) flagged this general class of risk in the abstract. Actually building and verifying it surfaced three concrete, specific failure modes worth recording for Phase 2:

1. **The Docker Postgres image's default `POSTGRES_USER` is a superuser with `BYPASSRLS`.** Confirmed via `SELECT rolsuper, rolbypassrls FROM pg_roles`. The app's connection pool was first wired to this role — every RLS policy passed silently, including a read with zero session context set at all. Fix (`002_app_role.sql`): a dedicated `vetify_web_app` role, `NOSUPERUSER NOBYPASSRLS`, with only `SELECT`/`INSERT`/`UPDATE` grants — the app must never connect as the migration-owning bootstrap role. **Closed**: `lib/db.ts`'s `ensureNonSuperuser()` checks `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user` once (memoized) before the first transaction and fails fast if either is true — a checked invariant, not just a convention. Worth its own note: the first implementation hooked `pool.on("connect", ...)`, which is *not* awaited by `pg` before handing the client back to its caller — the check ran concurrently with the caller's own queries on the same client, reproducing the exact "client already executing a query" race `pg`'s own deprecation warning flags. Fixed by using a separate `pool.query()` (its own checkout/release cycle) instead of sharing the connecting client.
2. **A `FOR ALL` write policy widens `SELECT` too.** Postgres OR-combines every applicable *permissive* policy per command, and `FOR ALL` applies its `USING` clause to `SELECT` as well as `INSERT`/`UPDATE`/`DELETE`. The original `business_onboarding_write` policy (role-recognized-but-not-tenant-scoped) silently let business2 read business1's full row — including director NIN/BVN — past the dedicated tenant-scoped `_select` policy. Confirmed live over the running API, not just in psql. Fix (`003_fix_write_policy_select_leak.sql`): split every `FOR ALL` into explicit `FOR INSERT`/`FOR UPDATE` (no `FOR DELETE` — this schema never physically deletes rows, so leaving it un-policied denies it outright). **This is the single most important lesson for Phase 2's ~90-table fan-out**: any codegen pass generating RLS policies must never emit `FOR ALL` for a write policy on a table that also has a narrower `SELECT` policy.
3. **RLS write policies shouldn't re-encode per-choice authorization.** `approved_business`'s insert policy was first written to require `party_role = 'vetify'`, copying `ApprovedBusiness`'s Daml signatory directly — but the row is actually created by `ApproveCompliance`, whose Daml controller is `verifier` alone. This works in Daml because exercising a choice on a `vetify`-signed contract propagates `vetify`'s authority into that choice's body — a mechanism with no direct SQL equivalent. Fix (`004_fix_approved_business_write_scope.sql`): RLS write policies stay a coarse "some recognized session" backstop; the real per-choice gate is `lib/auth/withAuthorization.ts` (addendum D), which was already correctly scoped (`approveComplianceImpl` wrapped with `withAuthorization(["verifier"], ...)`) — the bug was solely in the redundant, over-narrow RLS layer duplicating that check incorrectly. **Confirms addendum D's framing directly**: Daml's authorization model does real work beyond a role check, and a naive one-to-one translation of "this template's signatory" into "this table's RLS role" breaks on exactly this pattern.

### Go/no-go read against addendum C's Phase 1 criteria

1. *Every `assertMsg` has a unit-tested TypeScript guard with identical error text* — **done**: `apps/web/test/domain-onboarding.test.ts` and `test/domain-compliance.test.ts` (42 tests total across all three suites, `node:test`, run via `npm test`) cover `validateBusinessOnboarding`'s ensure-clause translation as pure-function tests, plus every choice function's guards and happy paths as real-DB integration tests (unique CAC per test, cleaned up via a dedicated superuser client afterward — the app pool itself has no `DELETE` grant by design, so cleanup can't route through it). Each `withAuthorization` role gate is also directly tested (e.g. a `vetify` session calling the `verifier`-only `approveCompliance` correctly throws `AuthorizationError`).
2. *Automated test matrix proving RLS blocks cross-party reads* — **done**: `apps/web/test/rls.test.ts` automates the manual `psql`/`fetch` probing from the first pass — every test opens its own `BEGIN`/`ROLLBACK` so fixtures never touch committed state. Includes a direct regression test for bug #3 (`approved_business` INSERT as `verifier`, the exact case that broke). Writing this surfaced a genuine Postgres RLS nuance worth flagging for Phase 2's codegen: `INSERT ... RETURNING` also enforces the table's **SELECT** policy on the returned row (since `RETURNING` re-reads it) — a `business`-role insert must already have its own `app.current_cac_reg_number` matching the row being written, or the `RETURNING` clause itself raises the RLS error even though the `INSERT`'s `WITH CHECK` alone would have passed. Not a bug (real usage already satisfies this, since a business's session `cacRegNumber` is exactly what it writes), but a subtlety any future codegen-generated insert path needs to account for.
3. *G14 EDD gate / policy maker-checker byte-identical decisions* — not applicable; both are out of scope for this slice (see above).
4. *No discovery implying the remaining ~90 templates need redesign, not translation* — **holds, with a caveat**: the three bugs above were all in the RLS/infrastructure layer, not in the choice→transaction-function translation pattern itself (every `assertMsg`, `fetch`, and `create` ported mechanically and worked on the first pass once the RLS layer was fixed). The translation premise survives Phase 1; the RLS-authoring premise needed real correction that must now be carried into Phase 2's codegen design.

**Net**: proceed to Phase 2, but only after promoting lessons 1-3 above into whatever generates the remaining ~90 tables' RLS policies — otherwise the same three bugs reproduce at 90-table scale instead of being caught once here. **Update**: points 1 and 2 above are now closed (runtime invariant + automated test suite, both described just above) — the one remaining Phase 1 gap before Phase 2 is generalizing that suite's *pattern* (not its specific test cases) into whatever generates RLS policies/tests for the next ~90 tables, since today's suite is hand-written per table, not derived from the same codegen pass §1 proposes for the schema itself.

1. **RLS's tenant-scoping can pre-empt a business-rule check in a way that changes the error message a test should expect.** `AcceptProposal`'s G11 gate is supposed to catch "certification is for a different facility" — but if the certification belongs to a *different tenant* (not just a different facility for the same tenant), `shariah_contract_certification`'s own `SELECT` policy blocks the read before the facility-match code ever runs, surfacing `"Certification not found"` instead. ## Codegen Experiment

Every prior pass ended with the same open question: does the hand-authored translation pattern survive being mechanized for the remaining ~80 tables? This pass built an actual (if deliberately limited) codegen tool — `apps/web/scripts/codegen/{parseDaml,genSql,genDomain,run-codegen}.ts` — and ran it against `daml/Vetify/Governance.daml`'s five registry templates (`AuthorizedOfficer`, `PolicyApprover`, `AuthorizedAssessor`, `AuthorizedSentinel`, `AuthorizedAdvisor`), a module never touched by any prior pass. Three of the five are near-identical in shape (vetify signs, a named party observes, `Deactivate*`/`Reactivate*` choices with shared-helper-derived guards) — chosen deliberately as the strongest test of "does codegen handle real repetition," not the weakest.

**What the tool is, and isn't**: `parseDaml.ts` is a line-scanning parser targeting this codebase's consistent 2-space-indent Daml style — not a general Daml/Haskell grammar. `genSql.ts`/`genDomain.ts` translate the parsed IR into a Postgres migration and a TypeScript domain-function file. This tests whether the *translation rules* generalize, not whether a from-scratch Daml compiler is feasible in this timeframe — a fair scope given the actual question is "can this be mechanized," not "can a full parser be built quickly."

### Real bugs found and fixed while building the tool itself (not the target Daml)

1. **A regex `\s*` ate a field's leading indentation, corrupting block-indent detection for every field after the first.** `create this with\s*\n?` used `\s*` (which matches newlines) before the optional `\n?`, so it silently consumed the first field line's own leading whitespace along with the newline — the create-field extractor's "same indent = same block" logic then saw the first field at indent 0 and every subsequent field at indent 10, misread as "unexpectedly nested," and dropped all but the first field. Fixed by requiring `[ \t]*\n` (trailing same-line whitespace + a mandatory newline) instead of a newline-matching `\s*`.
2. **assertMsg calls whose message is a shared helper function are invisible to a template-scoped parser.** `DeactivateOfficer`'s body calls `requireCanDeactivate "Officer" active reason performedBy` — a call to a top-level helper, not an inline `assertMsg`. The first parser pass produced `asserts: []` for every `Deactivate`/`Reactivate` choice in the file. Fixed by also parsing top-level `name : ... -> Update ()` functions (`parseDamlHelperFunctions`) and cross-referencing calls to them from inside a choice body (`findHelperCalls`), substituting the call's actual arguments for the helper's parameter names.
3. **~20 call sites codebase-wide use a *dynamic* assertMsg message** (`assertMsg (entityLabel <> " is already inactive") active`), not just a literal string — the original regex only matched the literal-string shape and silently dropped every dynamic one. Fixed by detecting the parenthesized-expression shape too and carrying the raw expression through for the generator to render as a template literal.
4. **Generated JS referred to bare Daml identifiers with nothing in scope binding them** (`if (!(active)) throw ...` — `active` is a template field, `reason`/`performedBy` are choice args, neither exists as a bare variable in the generated function). Fixed by qualifying every recognized identifier to `args.x` or `row.snake_case_x` before any other translation step runs.
5. **`not active` (no parens) didn't match the `not\s+\(` translation rule** and was left as invalid JS (`if (!(not active))`). Fixed with a second, bare-identifier translation rule.
6. **A subtle interaction between two correct-in-isolation steps produced wrong output together**: qualifying identifiers on the *raw* dynamic-message string before splitting on `<>` also matched the English word "active" inside the literal-text portion of the message (`" is already active"`), rewriting it to `" is already row.active"`. Neither step was buggy on its own; qualifying needed to happen *after* splitting the message into `<>`-joined segments, applied only to non-string-literal segments. This is the kind of bug that only appears when composing two mostly-correct passes and is exactly the class of thing worth testing for before scaling to 90 tables.

### The judgment call codegen can't make on its own

A `Party`-typed field (e.g. `assessor : Party` on `AuthorizedAssessor`) is ambiguous by name alone: it could be a fixed framework role encoded via the RLS session role (like `vetify`, dropped as a column entirely) or the registry's actual identity key (becomes a real column). Nothing in the Daml syntax distinguishes these — `run-codegen.ts` takes a small hand-written config per template naming which is which. This is a legitimate, permanent limitation, not a bug to fix: a domain-specific decision needs a human or an explicit hint, not a heuristic guess.

One generated-but-inert consequence of this: the tool correctly generated a self-access RLS clause keyed on a per-individual `app.current_party_id` session variable, mirroring Daml's per-Party observer field exactly — but this system's `SessionContext` has no per-individual identity, only one shared role per party type (`CLAUDE.md`'s documented "many users share one Canton party" design). The clause was simplified to a blanket per-role check in the applied migration; the generated version wasn't wrong, just ahead of what this system's session model currently supports.

### What still needs a human after all six fixes

The `create this with active = False, lastUpdatedBy = Some performedBy, ...` → SQL `UPDATE` translation was deliberately left as an honest `// TODO` marker rather than guessed at — unwrapping `Some x` and knowing `t` refers to a `t <- getTime` bound earlier in the same do-block both need real semantic understanding the line-scanner doesn't have. This was finished by hand for all five registries (a few lines each, mechanical once the guards were already correct) — the single largest remaining gap in the tool as it stands today.

### Result

68 → 75 tests, all passing on the first real run once the six fixes above landed — `registerX`/`deactivateX`/`reactivateX`/`requireActiveX` all working correctly for every one of the five registries, including the two (`AuthorizedAssessor`, `AuthorizedAdvisor`) that close a gap explicitly deferred in the Financing and Murabahah passes (`beginUnderwriting`/`certifyShariahTerms` never actually checked a registry before this). **The codegen question has a real, if qualified, answer now**: the mechanical translation pattern *does* generalize — every bug found was in the *tool*, fixed once, and then correct across all five templates simultaneously — but "mechanical" still means a human has to (a) supply per-template config for genuinely ambiguous cases, (b) finish the record-update translation by hand, and (c) review the output before trusting it, the same discipline addendum D already named for hand-written domain functions. That's a meaningfully smaller lift than hand-authoring all ~80 remaining tables from scratch, but it is not "point at Daml, get a working migration" either.

**Closed a real gap the codegen pass left behind**: `registerSentinel`/`deactivateSentinel`/`reactivateSentinel` existed in `lib/domain/governance.ts` since the Governance codegen slice, but — unlike its `AuthorizedAssessor`/`AuthorizedAdvisor` counterparts — no `requireActiveSentinel` function was ever written. Added it, mirroring the other two exactly, and wired it into `flagDelinquent`/`resumeActive` — inlined against the same client/transaction rather than calling the standalone export, so the registry check and the contract row lock stay atomic (calling the separately-`withTransaction`-wrapped export would have opened a second pool connection and lost that atomicity — a subtlety the assessor/advisor gates never had to confront, since nothing before this slice actually called them from inside another domain function).

**Two real RLS bugs found live, both the same root cause recurring**: Postgres's `INSERT ... RETURNING` re-reads the row through the table's `SELECT` policy, not just the `INSERT` policy's `WITH CHECK` — first discovered in the Phase 1 pass, and it bit twice more here:
1. `murabahah_contract`'s `SELECT` policy (from Stage 8) never included `sentinel` — so a sentinel session's own `FlagDelinquent`/`ResumeActive` failed with `"MurabahahContract not found"` on the `SELECT ... FOR UPDATE` lock, even though sentinel is a real observer of `MurabahahContract` in the Daml original. Fixed by adding `sentinel` to the policy (alongside the new `UPDATE` policy Stage 8 never needed, since it never mutated a contract post-creation).
2. `audit_event`'s `SELECT` policy only allowed `vetify`/`financialInstitution` — so the same sentinel session's `INSERT INTO audit_event ... RETURNING id` failed RLS on the `RETURNING` step, even though its `INSERT`'s `WITH CHECK` alone passed. This one is a genuine REST-layer concession, not a privacy-model match: the real Daml `AuditEvent` has no sentinel signatory/observer clause at all (only `vetify` signs, `financialInstitution` observes) — sentinel merely *authors* it via `FlagDelinquent`/`ResumeActive`'s dual controller and has no ongoing ledger-level right to read it back. Postgres has no way to say "may insert and read back the one row just inserted, but not others" without a session-scoped predicate this schema doesn't carry, so `sentinel` was added to the `SELECT` policy outright — a slightly wider grant than the Daml original, noted rather than silently matched.

**Verified end-to-end live against the running app**, not just via tests: registered `sentinel` in `authorized_sentinel` directly (no `/api/governance/sentinels` route exists yet — the codegen pass only wired routes for `assessors`/`advisors`, not `officers`/`policyApprovers`/`sentinels`; a pre-existing gap from that pass, not something this slice needed to fix), then against the live `Active` `MurabahahContract` (id 2, `FAC-2026-STAGE8-1`, `business1`/`RC1234567`) left over from the Stage 8 pass: `fi1` → `RecordPayment` on installment 1 (paid today, against a `2026-01-01` due date — genuinely late) correctly dropped the balance from 550,000 to 504,166.67, advanced `installmentsPaid` to 1, and created both a `RepaymentRecord` and a `LatePaymentCharity` obligation (uncharged, unsettled, per scope). `sentinel1` → `FlagDelinquent` → `ResumeActive` correctly cycled the contract's status and created two `AuditEvent` rows, visible to `fi1` and correctly invisible to `business1` (confirmed live, not just asserted) — the one table in this entire migration where the business is deliberately not a reader.

**Addendum A/C lessons held a fourth time**: `outstanding_balance`, `amount_paid`, `charity_amount`, etc. are `NUMERIC` from the first draft; every write policy is `FOR INSERT`/`FOR UPDATE`, never `FOR ALL`. 75 → 87 tests (10 domain + 2 RLS), all passing.

**Net**: four modules deep now (Onboarding/Compliance, Financing, Murabahah in full, Governance registries), and the recurring finding across this whole exercise keeps being the same one — RLS's `SELECT`-policy-gates-`RETURNING` behavior is easy to forget per new table, cheap to fix once caught, and this slice is the second and third time it's bitten a table modeled after a Daml template whose observer set doesn't cover the party actually performing the write. Worth stating as a standing checklist item for any future table: *whichever role INSERTs also needs to be in that table's SELECT policy, even if the Daml original's signatory/observer clause doesn't literally name it.*

Picks up the piece the eighth slice explicitly deferred: `DirectDebitMandate` (create + `SuspendMandate`/`ReinstateMandate`/`CancelMandate`), `DirectDebitCollectionAttempt` (an immutable record — no choices at all in the Daml source), `MurabahahContract`'s `RecordRecoveryPayment` (needed because `GSMInvocation`'s `RecordGSMSweep` routes every balance change through it), and `GSMInvocation` (create + `RecordGSMSweep`/`CancelGSM`). Procedural, FI-driven workflow (the Collections Agent per CLAUDE.md) — no scored judgment anywhere in this slice, a deliberately different shape from every officer-gated or sentinel-scored choice built so far. **A real atomicity bug caught and fixed before it ever ran, not found live.** The real Daml `RecordGSMSweep` choice explicitly composes `exercise contractCid RecordRecoveryPayment` — one ledger transaction, atomic by construction. The first draft of `recordGsmSweepImpl` called `recordRecoveryPaymentImpl` directly, which itself opens its own `withTransaction` (a fresh pool connection, its own `BEGIN`/`COMMIT`). That's two independent transactions masquerading as one: a GSM sweep that recovered money in one transaction but failed to update the invocation's `last_sweep_ref`/`status` in a second, separate transaction would leave the system in a state neither "swept" nor "not swept" describes correctly. Caught by re-reading the plan before running it, not by a failing test (nothing in the test suite would have detected this — both individual transactions would have committed successfully in isolation; only genuine concurrent failure between the two commits would ever have surfaced it, and by then it's a production incident, not a red test). Fixed by extracting `recordRecoveryPayment_onClient(client, ...)` — a version of the same logic that takes an already-open client instead of opening its own transaction — mirroring `checkFourEyes`'s existing precedent in this same file (helpers meant to compose atomically with a caller's own transaction are written to accept a `client`, not to call `withTransaction` themselves). **This is a distinct failure mode from the eighth slice's controller-placement bug**: that one was caught by live-clicking a wrong button and got a real `403`; this one had no such trigger — a broken transaction boundary produces correct-looking results on the happy path and only breaks under real concurrent failure, exactly the kind of bug a live-verification pass cannot reliably catch either. Worth naming as its own category alongside "does every domain export have a route" and "is the controller party correct": **whenever one choice's Daml source composes `exercise` on another contract, the ported version must call a client-scoped helper, never a `withTransaction`-wrapped top-level export, or the composition silently stops being atomic.**

**Net**: 15 new tests (13 domain + 2 RLS), both automated checks still clean (38 tables, 99 routable exports), and a real cross-transaction atomicity bug caught by design review rather than by a failing test or a live click — a reminder that the test suite and the live-verification pass each catch different bug classes, and neither is a substitute for actually re-reading composed-choice logic against its Daml source before running it.

## Phase 2, Seventeenth Slice — EDDCase (G14 Enhanced Due Diligence)

### New risks this pass of slices surfaced, that Phase 1 alone didn't

- **Every UI pass has found at least one real bug invisible to API-level tests alone** — the archived-`financing_request`-vanishes-from-the-decisions-list bug (Financing UI pass) and the unarchived-`AssetPurchaseRecord`-reappears-in-the-queue bug (Murabahah UI pass) were both caught only by a human clicking through a live queue, not by the 87-101 passing automated tests at the time each was found. This generalizes Phase 1's own point 2 finding (the Compliance Dashboard reappearance bug) from "happened once" to "happens reliably, every time a new list-view ships." **A UI pass is not optional verification for any future slice — it is where a distinct class of bug lives that the test suite structurally cannot see** (list-composition bugs, not choice-logic bugs).
- **A genuinely new party role costs more than a new registry.** Adding `regulator` (Reporting slice) required real changes to `lib/auth/AuthContext.tsx` and `components/Layout.tsx` beyond anything Governance's five registries needed, since every earlier new party (`assessor`/`sentinel`/`advisor`) mapped onto the pre-existing `vetify` nav bucket. All 7 non-`business` Canton parties this system will ever need now have a mapped role, so this specific cost is behind this migration — but it's worth naming for any other Daml→Postgres migration attempting this pattern.
- **Registry/route coverage gaps compound silently across passes, not just within one.** `registerOfficer`/`registerPolicyApprover` existed as fully-working domain functions for two entire slices (the original Governance codegen pass, then the Financing UI pass) before anyone noticed no API route ever exposed either one. A "does every exported `lib/domain/*.ts` function have a corresponding route" audit script would catch this class of gap mechanically, rather than relying on a UI pass stumbling onto it by accident — the same kind of structural check addendum D already recommends for authorization, applied to route coverage instead.

### Go/no-go read

**The translation premise is now confirmed across five slices, not one — proceed.** No discovery in any of the four Phase 2 slices implied that any remaining template needs redesign rather than mechanical translation; the RLS/route-coverage risks above are real but each has a concrete, cheap, mechanical fix (an RLS symmetry check, a route-coverage audit) rather than a design rethink. Before continuing further into the remaining 72 templates, promote both checks above from "manual lesson" to an actual script or CI step — otherwise the same two bug classes will keep recurring at the same rate, just against a larger surface each time.

**Update — both checks now exist**: `apps/web/scripts/check-rls-symmetry.ts` reads every policy from `pg_policies` and flags any table where a role covered by an `INSERT`/`UPDATE` policy isn't also covered by that table's `SELECT` policy (extracting role literals from the `qual`/`with_check` expressions after stripping the two known `current_setting(...)` calls). `apps/web/scripts/check-route-coverage.ts` statically scans every export in `lib/domain/*.ts` (excluding `requireActive*`/`validate*` internal helpers) against every `import { ... } from "@/lib/domain/..."` across `app/api/**/route.ts`, and flags anything exported but never routed. Both run clean against the current schema/codebase (23 tables, 61 routable exports) — confirmed live that the route-coverage script actually detects a real gap, not just passing by accident, by temporarily removing a working import and re-running it. Wired into `npm run check` (`check:rls` + `check:routes` + `npm test`) as one combined command. Neither is wired into an actual CI pipeline yet (this project has none) — that wiring, whenever CI exists, is the last mile addendum D and this assessment both call for.

### What's not yet true, said plainly

- **No historical velocity data exists to convert "five slices done in one extended session" into a calendar estimate for a real team.** The original 6–8 month, 2–3 engineer estimate for the full migration is unchanged and no less unvalidated than before — this effort proves the *pattern* holds, not a *rate*.
- **Nothing has been committed to git.** All of it — 9 migrations, 6 domain modules, 22 pages, a partial codegen tool, 101 tests — exists only in one machine's working tree (`git status` shows a single untracked `apps/` directory entry, 0 commits touching it). Independent of any architectural question, this is the largest immediate operational risk on the table right now.
- **Phase 3 (the remaining ~5 of 27 pages), Phase 4 (agents rewiring), and Phase 5 (hardening: genuine maker-checker split, cookie sessions, rate limiting)** remain entirely untouched, unvalidated design — nothing in this assessment should be read as progress against those.
